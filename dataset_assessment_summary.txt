JBB-Behaviors 与 PII 数据集在当前 benchmark 中的适配性分析

1. 当前 benchmark 的基本要求
当前仓库的评测逻辑默认要求数据集必须满足标准二分类 benchmark 的 schema，核心字段包括：
- sample_id
- text
- label
- label 必须为 0 / 1

这意味着当前评测脚本更适合用于如下任务：
- harmful vs benign
- unsafe vs safe
- jailbreak vs normal
- toxic vs non-toxic

这些任务的本质都是“文本是否属于某一类风险”，因此可以直接进入当前 evaluate.py 的统一计算流程。

2. JBB-Behaviors 的定位
JBB-Behaviors 是一个 jailbreak / 安全风险 benchmark 数据集，核心目标是评估模型是否能够识别越狱、绕过安全策略、以及执行有害或违规的指令。

它本质上是一个风险识别数据集，不是通用 NLP 数据集。它并不是直接一张标准的 text + label 表格，通常需要我们做如下处理：
- 选择文本字段（例如 prompt / behavior / request text）
- 确认正负样本定义
- 建立 benchmark label 映射
- 例如：harmful / jailbreak / unsafe -> 1
- benign / safe -> 0

也就是说，JBB-Behaviors 可以接入当前 benchmark，但前提是先做标准化，并明确 label 的定义。

3. judge-comparison 的定位
judge-comparison 更像是评测器比较/判定一致性分析数据，而不是主 benchmark 数据。

它的作用主要是：
- 比较不同 judge / annotator / scoring 逻辑是否一致
- 检查 benchmark 质量
- 分析为什么某些样本的 label 或预测存在歧义

它不应该直接作为当前二分类 benchmark 的主评测数据，因为它更接近分析数据，而不是标准 benchmark 样本。

4. PII 数据集的定位
PII 数据集（例如 ai4privacy/pii-masking-300k）更偏向隐私信息检测、PII 类型识别和脱敏任务，而不是当前 benchmark 的安全二分类任务。

它通常涉及：
- 是否包含 PII
- 属于哪种 PII 类型（邮箱、手机号、身份证、银行卡等）
- PII 在文本中的位置
- 是否需要 mask / redact
- 是否涉及隐私泄露风险

这类数据通常不是简单的 text + binary label 结构，它更像是：
- detection task
- extraction task
- masking task

因此，PII 数据集不能直接放进当前 benchmark 流程，除非我们把它显式降维为一个更简单的“是否包含 PII”二分类任务。否则，应该单独设计它的评估模块。

5. 最终判断
- JBB-Behaviors：可以纳入当前安全 benchmark，但需要进行标准化和正负样本定义。
- judge-comparison：适合做辅助分析，不作为主评测集。
- PII：通常不适合直接接入当前二分类 benchmark，需要单独设计评估模块或做任务降维。

6. 实施建议
如果要在当前仓库中支持这两个场景，推荐采用分层方案：
- 主 benchmark：Toxigen / HateCheck / AEGIS2 / 标准化后的 JBB
- JBB 单独做 benchmark 化处理，确保 label=0/1
- judge-comparison 单独作为评测分析数据，不进入主 eval
- PII 单独做 pii detection / pii masking 的评估逻辑

7. 总结
当前 benchmark 的底层假设是“标准二分类 benchmark”，因此它对 jailbreak 和 PII 这类数据集并不是天然兼容的。

真正的关键不在于代码能否 load 数据，而在于：
- 数据是否满足 benchmark 任务定义
- 是否有稳定的 gold label
- 是否能映射到当前评测框架的输入格式

只有满足这些条件，数据才适合进入当前 evaluate 流程。
